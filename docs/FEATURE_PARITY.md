# Paperless-ngx feature parity contract

Baseline: Paperless-ngx **v3.4.2**, released 2026-11-03. Ripiano is independent; this table defines behavior to preserve, not code to copy. Product improvements are defined in [PRODUCT_SPEC.md](PRODUCT_SPEC.md). The implementation must expand each row into API and end-to-end scenarios before marking it complete. A later Paperless release does not silently expand this pinned baseline.

Milestones: **R1** = safe daily archive; **R2** = full daily workflow and physical filing; **R3** = advanced management and integrations; **R4** = verified parity. R4 requires every row below, including optional features when explicitly enabled. Earlier releases may be useful without claiming full parity.

| Capability to preserve | Ripiano behavior / improvement | Target gate |
| --- | --- | --- |
| Web upload, drag-and-drop, consume folder, scanner imports, API upload | All channels reach the same durable ingestion pipeline; PWA and Android capture add simpler mobile paths. A retried upload with the same scan ID and the same file returns the existing document; the same scan ID with a different file is refused (409). Originals download under the extension of the detected type (a PDF named `.png` downloads as `.pdf`). | R1-R2 |
| Additional external inputs | Optional Telegram private-chat bot first; S3 and Google Drive adapters use the same durable ingestion contract. Implemented: a Sources screen where each person connects external storage as an input, set up entirely in the app (encrypted credentials, folder, recursive option, include/skip patterns, file types, size and date filters, leave/move/delete after import with a grace period for moved files, optional filing, preview, and check now). S3-compatible storage, WebDAV (Nextcloud, ownCloud, Synology), Google Drive, OneDrive, Dropbox (OAuth "Connect account", sign-in apps managed by the archive owner), folders on the NAS, and Telegram bots (token pasted in the app, chats approved on the card) are available. | R1-R3 |
| Incoming email accounts and filtering rules, including OAuth-capable providers | Import attachments with source metadata; email configuration lives in Integrations. IMAP accounts (password or Gmail/Outlook OAuth) and ordered rules with sender/subject/text/file-name/age filters, mark-read/flag/move actions, and tag/sender/type assignment are implemented; imported documents show the sender, subject, and mailbox. Ripiano never deletes mail. A rule can import the whole .eml message, attachments, or both; the original message bytes are preserved. | R3 |
| PDF, image, Office, and email file processing through optional converters | Preserve originals; produce searchable previews/archive versions where supported; show unsupported-format errors. DOCX/XLSX/PPTX, legacy DOC/XLS/PPT, OpenDocument ODT/ODS/ODP, RTF, and EML intake with private conversion are implemented; emails render from escaped text without remote content. Outlook .msg is implemented too: it is read locally with olefile (subject, sender, date, text, attachment names) and rendered like an .eml. | R1-R3 |
| OCR, selectable text, PDF/A, language settings, reprocessing | Local default; retry/reprocess without losing originals; compare OCR engines on actual scans. A damaged PDF (one the plain PDF reader cannot open, or with more pages than OCR recovered) is not presented as complete: the original is kept, OCR's repaired pages become the searchable PDF (downloadable, with page previews), and the document is processed with `processing_warning: "damaged_pdf"` and a message asking to compare it with the paper and re-scan. It stays in the Inbox and the Overview's warning count until the owner marks it checked; it is not offered as a failed retry (`archive/tasks.py` `pdf_is_damaged`, judge 1 round 8 M2). | R1-R3 |
| Barcode/QR extraction, ASN detection, tag barcodes, split pages | Support documented paper scan workflows; physical-copy stickers add a separate stable identity. Local QR/1D barcode reading is implemented: PATCHT separator sheets split PDFs while the full scan is kept as a hidden source, ASN codes set a per-owner unique archive number (editable and searchable as `asn:`), and TAG: codes add existing tags. Each tag can also map one owner-unique barcode value, with a printable QR label; mapped scans add a source tag while respecting manual removals. ASN barcodes also start separate documents without a PATCHT sheet, retaining each barcode page and the unchanged full scan. | R2-R3 |
| Tags, nested tags, correspondents, document types, storage paths, dates | Keep all metadata fields; create and move nested tags without cycles, and let parent Library filters include descendants; replace manual filing with suggestions and exception review. A disposable NAS year/tag browse copy exists. User-defined storage paths (templates with {correspondent}, {document_type}, {year}, {month}, {day}, {title}, {asn}, {tag}, {source}, and added-date placeholders) are chosen per document and lay out the browse copy; managed originals never move. Document dates are filled during processing from the first plausible date in the text (Italian/English written and numeric formats, day-first by default via `RIPIANO_DATE_ORDER`), or from the email Date header; email senders are filed only when they exactly match an existing correspondent; manually set or cleared dates are never replaced (`archive/date_detection.py`, `test_date_detection.py`). | R1-R2 |
| Typed custom fields and document links | Create/edit/filter/search fields and links with permissions; preview and atomically convert compatible field values before a type change | R3 |
| Exact, fuzzy, rule-based, and learned matching; suggestions | Rules plus a local learned model and correction examples; explain why suggestions appear. Optional example suggestions exist: the document dialog offers tags, senders, and types from the owner's manually filed similar documents, showing the example and its distinctive shared words; tapping a suggestion saves that field immediately while other draft edits still require Save changes. Tag, sender, and type rules match by exact phrase, any word, all words, similar spelling (fuzzy), or regular expression; regex search runs with a 0.25 s timeout over at most 100k characters, and fuzzy rules have at most 6 words. A local learned classifier (Naive Bayes per sender, type, and tag, trained only on the person's own manual filing, nightly and on demand) adds suggestions with a calibrated probability: held-out folds fit Platt scaling, suggestions appear only at 60% or more, and Tags & filing shows held-out precision and coverage. The owner may opt into applying predictions to new documents after OCR, but only above 90% calibrated confidence, 95% held-out precision and 20 held-out suggestions per field at that same 90% threshold, without replacing manual/input choices or removed tags. Older documents are not backfilled automatically; a person can select up to 100 existing documents for a one-time local-model filing pass. Rechecks after a rule change run in 2-second slices on the maintenance queue, so mail and source imports interleave. Suggestion reasons list shared words from the document text, not from a title that is still the file name. For EML and MSG examples, comparison ignores recipient addresses, dates and header labels while keeping the sender, subject and message; the original OCR remains searchable. | R2-R3 |
| Optional AI suggestions, similarity search, document chat | Opt-in provider selection, including local endpoints; show when content would leave the NAS. Implemented: local "similar documents" (word-overlap similarity, with exact and likely duplicates flagged) without any model or external call. Intentional change (see docs/DECISIONS.md D1): AI suggestions and document chat are served through MCP agents rather than by Ripiano calling a provider. Optional semantic search (off by default) finds passages by meaning with an embedding model on Ollama or an optional NAS embedder, merges keyword and meaning matches into the main Library ranking only when enabled, and gives agents a `semantic_search` tool that returns passages for their own model to answer from | R3-R4 |
| Full-text search, field syntax, snippets, filters, sort, saved views | Search-first Library with simple filters and a power-user query mode; saved collections. Query syntax: field terms (`title:`, `text:`, `note:`, `tag:`, `sender:`, `type:`, `sticker:`, `asn:`, `field:`, `is:`), exclusion with `-`, `OR` between terms, and date years/months/ranges/comparisons on `date:`/`created:` and `added:` (`archive/search_syntax.py`, tested in `test_search_syntax.py`). Paperless's full Whoosh syntax (wildcards, fuzzy `~`, proximity) is not reproduced; PostgreSQL full-text ranking is used instead. `is:tagged` and `is:untagged` narrow results without creating a mandatory filing queue; Overview links directly to untagged documents. A saved Paper copy filter finds documents with a registered physical copy (including missing copies), those kept only digitally, or copies reported missing. Full-text search is language-aware (Italian and English stemming on a stored tsvector, exact forms rank first; common accents are folded for typing without them, with small-batch backfill of older vectors; `archive/fulltext.py`, migrations 0055–0057), and field terms also accept Italian names (`mittente:`, `etichetta:`, `data:`, …). Plain search words also match the original file name. | R1-R4 |
| Duplicate detection and duplicate review | Exact/likely duplicate view; never silently throw away a captured original. Exact copies are flagged at upload and reviewed in Inbox; likely duplicates (≥85% word similarity) are flagged in each document's Similar documents | R2-R3 |
| Preview, original/archive download, notes, document history | Show common actions first; retain underlying versions and audit events. Implemented: a per-document audit history (`DocumentEvent`, `archive/history.py`) records who or what changed the title, date, sender, type, storage path, ASN, tags, or custom field values (person, agent grant, workflow, email rule, source, matching rules, learned filing, barcodes) with readable old → new values, plus upload with its input channel, new versions, Trash, and restore. Never records document text. Shown as Changes in the document panel and at `GET /api/documents/<id>/history` for anyone who can view the document; included in portable exports. Not recorded: follow-up status/notes edits, and filing copied onto barcode-split parts at creation. The document dialog shows the first page (the cached page image from Pages & versions) beside the form on wide screens and as an expandable strip above the fields on phones, with a placeholder while a non-PDF is still processing or when no page can be rendered; Library rows have no thumbnails, to avoid rendering a page for every row on the NAS. Edit-conflict protection: a save from a stale copy (`base_version` or `If-Match`) is refused with 409 for details someone else changed; the form merges their changes and offers **Use my value** per detail. | R1-R3 |
| File versions and merge-as-versions | Root metadata with version-specific file/text; explicit selection and history. Implemented: uploading a file, editing pages, or copying the current original from another owned document adds a version. Earlier files stay downloadable, can be made current again, are included in document exports, and are removed only by permanent deletion. The source document remains separate; automatic consolidation of metadata, notes, or physical copies is not implemented. | R3 |
| PDF rotate, split, merge, reorder, delete pages | Warn when an edit changes an original or invalidates a digital signature. Implemented: rotate, remove, and reorder pages save a new version (the previous file is kept); split pages into new documents; merge selected documents into a new PDF; digitally signed PDFs need explicit consent and keep the signed file as an older version. | R3 |
| Bulk edits, retagging, reprocessing, trash/restore, and opt-in retention | Preview and undo where possible; background job status for long actions | R2-R3 |
| Workflows: consume/add/update/scheduled triggers, filters, assignment/removal, email, webhook, password removal, AI actions | Guided recipes plus a full-width responsive editor opened on demand, with a live sentence summary, compact source choices and sticky save controls; deterministic execution and visible run history. Implemented: added, updated, and scheduled (days after a date) triggers; source, file-name, text, tag, sender, and type conditions; add/remove tags, set sender/type (never over manual choices), set title from a pattern (storage-path placeholders plus `{date}`, `{added_date}`, `{original_filename}`; validated on save, one line, at most 300 characters, never empty), set storage path, set custom field values (validated by field type), share with people/groups (view or edit; only adds or raises grants, never removes), needs-action, note, webhook (metadata only), and SMTP email with optional attachment; notes, webhooks, and emails are sent once per document, while "updated" workflows run again on every matching change; every run is in a visible history. Title, storage path, and custom field values a person changed by hand (a person-made change in the document history) are never overwritten; every workflow change, including sharing, is recorded in the document history under the workflow's name. Consume trigger: Paperless runs "consumption started" workflows before the file is stored; Ripiano's "added" trigger runs after OCR, rules, and detection and covers the same assignment use cases, except routing by file name before OCR (file-name conditions still work on "added"). Password removal is implemented as an "Unlock PDFs" action on added workflows: encrypted, write-only passwords are tried before OCR, the searchable copy is made from the unlocked file, and the original stays as uploaded. Intentional change (docs/DECISIONS.md D1): AI actions are not run by Ripiano; MCP agents (for example the local Mac worker) read documents and apply filing through their grants, and workflows can react to those changes with "updated" triggers. "Updated" workflows run after the owner's single-document edits, bulk tag/sender/type/date edits, and MCP agents' `change_document_tags` and `set_document_filing` changes; workflow actions never start further workflows. A workflow started by an agent's change never adds or removes the filter tag of another of the owner's active agents (the same tags the MCP tool refuses) and says so in its run detail, so an agent cannot widen another agent's view through a workflow (`archive/workflows.py` `guarded_tags`, tested in `test_round6_fixes.py`). | R3-R4 |
| Users, groups, object permissions, ownership, 2FA, OIDC/remote auth where applicable | Same access behavior across PWA, Android, REST, and MCP; agent grants and personal API tokens are additional restrictions (see the REST API row). Implemented: named MCP grants with separate search, OCR-text, tag, and sender/type scopes; the latter respects human/input-rule choices and records model origin. The optional local Mac worker can use both grants to suggest or, with separate write opt-ins, apply existing tags and fill empty sender/type fields. TOTP two-step sign-in has hashed single-use recovery codes, replay protection, and lockout. The Android client signs in through its embedded web app, so it uses the same code prompt; real-device validation is still pending. An admin adds people, resets passwords, turns accounts off, and manages groups (People screen and `/api/people`, `/api/groups`; API tokens cannot reach them). The owner of a document can share it with a person or a group as *view* or *edit details* (title, date, follow-up, notes); recipients find it under Shared with me, while filing, files, links, and Trash stay with the owner. Turned-off accounts, removed grants, leaving a group, and Trash end access. Groups and grants are included in `export_archive`. Tags, senders, document types, and saved views can be shared with a person or a group as "view and use" or "edit": recipients see them under Shared with me, filter what was shared with them by them, and file the owner's documents they may edit with the shared objects only, without clearing or replacing an unshared sender or type; edit also allows renaming. Deleting stays with the owner. Intentional change (docs/DECISIONS.md D3): OIDC/remote authentication is provided by an optional sign-in gateway in front of Ripiano (Traefik + Authelia, `deploy/gateway/`), not inside Ripiano; Ripiano keeps its own accounts, sessions, and two-step sign-in. | R1-R4 |
| Share links, expiring links, bundles, email sending | Off by default; original-file links expire and can be revoked. Implemented: bundles share selected originals as one expiring, revocable, checksum-verified ZIP link, and documents can be emailed (original or searchable PDF) through configured SMTP with an hourly limit and send history. New versions revoke links and bundles. Turning an account off revokes its links and bundles for good (`revoked_reason: "account_off"`; they answer like unknown links and stay revoked if the account is turned on again; docs/DECISIONS.md D9) A password change or an admin password reset revokes the person's links and bundles too (`revoked_reason: "password_changed"`, docs/DECISIONS.md D11). | R3 |
| REST API, API tokens, documented schema, task/status endpoints | Versioned API and OpenAPI, with permission parity and compatibility tests. Implemented: personal API tokens (hashed, expiring, revocable, last-used tracking). Intentional change from Paperless: a token reads, uploads, and files with its owner's access, but cannot sign in or change security, tokens, agents, people, or groups, cannot share with other people or create public links, and cannot send documents out or reconfigure what does (document email, mail, Sources, workflows, backups, archive settings) — `archive/api_tokens.py`, tested in `test_api_tokens.py` and a generated OpenAPI 3.1 outline at `/api/schema.json` covering every route, method, and path parameter. Version 1 contract: request and response body schemas for the 40 most-used operations are recorded from a realistic scenario (`archive/api_contract_v1.json`), published in `/api/schema.json`, and enforced by a compatibility suite that fails on removed fields, changed types, changed status codes, or removed routes. | R1-R4 |
| Dashboard, statistics, saved views, system monitoring and task controls | Home shows useful work without setup; advanced monitoring stays available. Implemented: personal dashboard collections (up to six pinned saved searches with live counts and recent documents; optional per-device dashboard start page) and an Overview with document, storage, follow-up, and processing totals; a "needs a look" list (unreadable, overdue, duplicates, mailbox errors, failed workflow runs); a 12-month intake chart with a table view; type, tag, and source breakdowns; and backup, mailbox, and workflow health. The archive owner also sees OCR and maintenance queue depth. Queued backups and NAS browse copies can be cancelled; failed or cancelled runs can be retried as a linked new run. A Background jobs section on Overview lists each person's queued, running, and failed work (text recognition, permanent deletion, filing-model learning, failed workflow runs) with cancel for queued documents and retry for failed jobs (`/api/jobs`, `/api/documents/<id>/cancel-processing`). A document whose worker stopped (no 30 s heartbeat for 2 minutes by the database clock) is flagged `stalled`, can be retried or cancelled, and is requeued by the scheduler after two checks in a row (about 3–4 minutes); three interruptions in a row mark it failed, counted apart from OCR failures. Each worker also reports every 30 s from a thread in its main process (`WorkerHeartbeat`, database clock); `/api/jobs` and `/api/overview` return a `processing` summary (`pending`, `processing`, `waiting_since`, `worker`, `problem`: `worker_not_running` or `queue_unavailable`) and a per-document `state` (`queued`, `waiting_for_worker`, `waiting_for_queue`, `processing`, `stalled`), with the same counts in both (hidden split sources left out). The Library and open document show the same worker or queue problem while visible documents are waiting; they check `/api/jobs` every 15 seconds and stop checking when none are waiting. A recipient opening a shared waiting document sees its own processing state and worker/queue guidance from the single-document response, without access to the owner’s `/api/jobs` list. A waiting document is queued once (`Document.queued_at`); the scheduler re-sends only documents never sent, or lost while the OCR queue is empty, so the queue never holds more than one message per waiting document. Each run holds a claim, so a run that was requeued or cancelled cannot save a late result or run workflows twice. Health: `/healthz` (database and queue server, 503 when down; status only when reached from outside), `/livez`, and an `mcp` healthcheck (docs/BACKUP_RESTORE.md). | R2-R4 |
| Export/import, maintenance, index rebuild, backup/restore | Open manifest and originals in single-document and selected-document exports; scheduled verified snapshots to mounted volume. Implemented: `export_archive` writes every account, record, original, older version, and searchable PDF with checksums to a portable folder, and `import_archive` loads it into an empty instance with all IDs and checksum verification. The search index needs no rebuild, because search runs in PostgreSQL. **Back up now** shows a running state and announces the result (finished, failed, cancelled). | R1-R4 |
| Search, metadata, and interface localization | Italian and English at minimum; no hard-coded text in components. English is the default; Italian can be chosen on the sign-in screen and sidebar, or follow the device. Implemented: every screen reads its text from per-component message files with English and Italian (type-checked to have the same keys), and the API translates its reviewed error messages for Italian clients. Every API message found by `archive/message_catalog.py` has an Italian version (enforced by `test_api_language.py`); field names inside messages use readable labels; Telegram bot replies follow a per-source language setting. Italian source strings have had a wording and terminology review; native-speaker review in the running browser remains before this row is verified. | R2-R4 |
| Keyboard shortcuts and accessible desktop interaction | Common actions and search are keyboard operable; mobile has touch-sized controls. Implemented: `?` shortcut list, `/` search, `N` add, `G`+letter screen navigation, `J`/`K`/Enter in the Library, a skip link, announced result counts and paper-copy moves, focus-trapping dialogs, mobile targets at least 44px for filing and document actions, and a browser test (`e2e/accessibility.spec.ts`) checking accessible names, labels, unique ids, alt text, heading order, and landmarks on the main screens. A full axe-core scan is not set up (adding the dependency needs approval). | R2-R4 |

## Additional Ripiano capabilities

These are not substitutes for parity rows: physical-copy hierarchy, printable document/container stickers (Find a sticker reads the QR with the camera where the browser has a QR reader, `StickerCamera.tsx`; elsewhere it says to open the QR with the phone's camera app), movement history, location contents that separate present copies from those reported missing, exception-only Inbox, first-class Needs action/reminders, installable iOS/Android PWA, Android native scanner, named per-agent MCP grants, optional daily local-PC worker, and scheduled backups visible in the app.

## Evidence required at R4

- Freeze and archive the upstream v3.4.2 documentation/API schema used for comparison; identify any capability missing from this initial table and add a row.
- For each row: automated API test where feasible and a real UI scenario for user-facing behavior. Record intentional behavioral changes with rationale.
- Cross-client parity check: a feature exposed in PWA must be available in the Android client, except that Android may add native capture behavior. Admin tools may use a responsive web view inside the client.
- Permission matrix tests for human users and at least two agents with different scopes and document filters.
- Representative Italian/English files, mixed document formats, duplicate scans, barcode sheets, signed PDFs, email attachments, and restore snapshots.
- No release is labelled Paperless feature-complete until every row is verified, not merely implemented in a hidden API.
